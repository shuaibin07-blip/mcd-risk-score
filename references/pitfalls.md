# 实测踩坑记录

开发过程中真实撞到的坑，写出来省得别人再造一遍。

## 协议层

1. **响应可能是 SSE 也可能是裸 JSON。**
   一开始只处理 JSON，调了半天没反应。`Accept` 头必须同时声明
   `application/json, text/event-stream`，解析时先判断有没有 `data:` 前缀。

2. **`Mcp-Session-Id` 要复用。**
   首次响应头里带，后续请求必须带上，否则部分工具拒答。

3. **结构化数据在 `structuredContent`，不是 `content[].text`。**
   `content[].text` 里夹的是给大模型看的 Markdown 说明，不要解析它当数据源。
   本项目只在 `structuredContent` 缺失时才退回从文本里抠 JSON。

4. **429 限流**：600 次/分钟。本项目是顺序调用 4 个工具，远低于阈值，
   但仍保留了"等待一次重试再报"的处理。

## 数据层

5. **字段名不统一。** 见 `MCP_INTEGRATION.md` 的容错表。同一个"实付金额"
   在不同响应里见过 5 种写法，必须按别名表取，取不到就返回 `None`。

6. **套餐子项要展开。** `comboItemList` 里才是真正吃到的东西，
   只统计主项名会漏掉热量和品类。

7. **营养表只能精确匹配。** `list-nutrition-foods` 返回的餐品名与订单里的
   商品名不一定完全一致，匹配不上就放弃该子项计分，不硬凑。

8. **券的到期字段见过 5 种写法**：`expireTime` / `endTime` / `validEndTime` /
   `expiryDate` / `endDate`。且日期可能是字符串也可能是时间戳（秒或毫秒）。

## 建模层

9. **缺失数据不能补零。** 补零会让分数虚低，等于造假。本项目所有缺失字段
   走中性分（60 或 65），并在报告里明说"该子项不计分"。

10. **集中度是 U 型不是单调。** 一开始写成"越集中越忠诚越高分"，
    后来发现这在授信逻辑里是错的——集中度过高是单点依赖风险。改成 U 型后
    评分卡才站得住。

11. **不要为了效果操纵演示数据。** mock 数据的随机种子固定为 1024，
    任何环境跑出来完全一致，报告上有 `DEMO DATA` 徽章标注，不冒充真实数据。
